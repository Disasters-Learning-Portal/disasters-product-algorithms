# Project Rules for AI Assistants

NASA Disasters product-algorithms repo: GeoTIFF → COG pipelines with S3 upload, consumed downstream by `veda-data-airflow`'s `build_stac` handler.

## Hard rules

1. **Library default `target_crs` / `dst_crs` is `EPSG:3857`** (Web Mercator). `cog_utils.convert_to_cog`, `main_processor.convert_to_cog`, and `SimpleProcessor` all default to it. Reason: airflow's `rio_stac.get_dataset_geom` crashes on EPSG:4326 outputs because modern PROJ writes the WGS 84 ensemble WKT + lat-first axis, producing `"Point outside of projection domain"`. Web Mercator sidesteps both. **Validated end-to-end** against veda-data-airflow's `build_stac` on a global Mollweide source (GAIA `total.tif`, reprojected with `needs_webmerc_clip()` auto-clip enabled) — the DAG accepted the output cleanly. **Do not change the library default back to EPSG:4326 without solving the ensemble + axis problem.**

   **Notebook templates default `TARGET_CRS = None`** (preserve native projection, no warp) with a commented `# TARGET_CRS = "EPSG:3857"` alternative immediately below. The operator opts in to Web Mercator when they're about to push through `build_stac`. Variable forwards to the CLI as `"-dst_crs", TARGET_CRS if TARGET_CRS else "native"`. If you regenerate a notebook from a template or add a new one, preserve this convention — do NOT default the notebook to `'EPSG:3857'` or `'EPSG:4326'` literal.

2. **Do not reintroduce a `normalize_wgs84_crs()` helper.** The old `gdal_edit.py -a_srs '+proj=longlat +datum=WGS84 +no_defs'` approach was deleted because PROJ re-canonicalizes the WKT back to the WGS 84 ensemble on read — the edit looked successful in `gdal_edit` output but the next consumer (`rio_stac.get_dataset_geom`) still saw ensemble + lat-first axis. The fix that actually works is **target EPSG:3857 in the first place** (rule #1 above). If you need to ship to EPSG:4326 specifically, you'll need a different mitigation (e.g. axis-order rewrite via low-level libtiff edit) — but don't add it back without a real test that proves the downstream consumer accepts it.

3. **Treat `TARGET_CRS`/`target_crs` as `None` when value is `None` / `""` / `"None"` (any case).** Means: preserve native CRS, skip the warp step entirely. Do not pass `--dst-crs None` to `rio warp` (OGR error 5). At the CLI boundary, the canonical sentinel for "no reprojection" is the string `"native"` — `process_landsat89`, `process_sentinel2`, `process_umbra`, and `process_capella` all map `-dst_crs native` → `None` before calling `convert_to_cog` (`process_satellogic` no longer exposes `-dst_crs` — it hardcodes native/`None` since PR #45). The notebook variable is `TARGET_CRS` (renamed from the older `DST_CRS` in this session; both still resolve correctly if found, but new code uses `TARGET_CRS`).

4. **If the source `.tif` has no embedded CRS, warn and skip reprojection.** Don't try to warp a CRS-less file.

5. **All temp files go to `/tmp/`** (never `./s3_temp` or any project-relative path). Don't reintroduce relative temp paths.

6. **GDAL must come from conda, not pip.** dylib version mismatches otherwise. Don't add `gdal` to pip requirements.

7. **Notebooks don't share kernel state across cells reliably** — testing-notebooks cells that import from `shared_utils` must contain their own `repo_root` discovery block, not rely on a "setup" cell having been run first.

8. **All raster hot paths use `NUM_THREADS=ALL_CPUS`.** `gdalwarp` calls include `-multi -wo NUM_THREADS=ALL_CPUS --config GDAL_NUM_THREADS ALL_CPUS`; `rio cogeo create` calls include `--co NUM_THREADS=ALL_CPUS`; `rasterio.warp.reproject` calls pass `num_threads=os.cpu_count()` (it needs an int, not the GDAL `ALL_CPUS` string). Don't drop these flags.

9. **Hub-image dep edits go in [`image/environment.yml`](image/environment.yml).** Post-consolidation (2026-05-28) the Disasters Hub image is built from this repo, NOT from a separate `pangeo-notebook-veda-image` checkout. The Dockerfile lives at [`image/Dockerfile`](image/Dockerfile); the conda env file is [`image/environment.yml`](image/environment.yml). Old artifacts that are GONE: the separate `pangeo-notebook-veda-image` repo (archived), the `hub-conda-deps.txt` file (deleted), the `sync-conda-deps.yml` cross-repo workflow (deleted), and the `ARG ALGORITHMS_REF` indirection (the algorithms code IS the build context now). Decision tree for a new dep is the same as rule #12 below — three audiences (pip / dev-conda / hub-image) → three files.

10. **`process_*` CLIs missing on a fresh hub pod is almost always a build-failure or path-filter issue, not a local-install bug.** Post-consolidation, the image is built by `.github/workflows/build-and-push.yaml` (prod, on push to `main`) and `build-and-push-dev.yaml` (dev, on push to `dev`) in THIS repo — no cross-repo dispatch. Common causes when a CLI is missing:
   - The Lint workflow OR the build workflow failed on the commit that produced the latest image (check `gh run list --branch <main|dev> --limit 5`).
   - The push didn't touch anything in the build workflows' **`paths` allowlist** (`image/**`, `src/**`, `pyproject.toml`, plus the workflow file) and intentionally didn't trigger a build. This is an allowlist, not a `paths-ignore` denylist (switched 2026-07-21) — a `dps/`-only, docs-only, or notebooks-only push fires no rebuild (all `.dockerignore`d out of the image anyway). Push a code change under `src/`/`image/` or use `workflow_dispatch` to force a rebuild.
   - The CLI entry point wasn't added to `pyproject.toml`'s `[project.scripts]` (lint should have caught this — see rule #11).

    **Check the Actions log for the relevant `build-and-push*.yaml` run before suggesting `pip install -e .` as a fix.** That workaround stays valid for hot-iterating local edits inside one hub session, never for "every fresh pod is broken."

11. **Before pushing, run `python tools/check_sensor_consistency.py` if your change touches `src/<sensor>/`, `pyproject.toml [project.scripts]`, or `[tool.setuptools.packages.find].include` — or use `python tools/new_sensor.py <name>` to scaffold both at once.** The scaffolder writes the four sensor files, both workflow notebooks, and both pyproject entries, then runs the consistency check as a post-condition (rolling back on failure). It ALSO pre-checks for **orphaned sensor dirs** (leftover sensor-shaped directories from prior rolled-back runs where `git restore .` reverted pyproject but didn't `git clean` the new untracked dir) and refuses to scaffold on top of a dirty baseline — the abort message includes copy-pasteable surgical and nuclear cleanup commands. Same checks run in CI on every PR via `.github/workflows/lint.yml`. The three failure modes the lint catches all shipped to production before being fixed: (a) console script registered without the package being installable (capella `ModuleNotFoundError`), (b) sensor dir exists without a console script entry, (c) notebook cell-0 frontmatter copy-pasted from another sensor without relabeling (capella's "processing Sentinel-2" leftover). Local invocation is <1s; cheaper than a CI cycle + hub rebuild cycle to discover the same bug.

    **Pre-commit hook (recommended):** install once per clone with `pip install pre-commit && pre-commit install`. After that, `.pre-commit-config.yaml` automatically runs the consistency lint on every `git commit` — no manual invocation needed. CI still runs the same check as a backstop for contributors who haven't installed the hook.

12. **Three dep surfaces, three audiences. Don't conflate.** `pyproject.toml [project.dependencies]` = pip-installable transitive deps (resolved by `pip install .`). `dev-conda-deps.txt` = local-dev + CI smoke conda deps (geospatial stack). `image/environment.yml` = hub-image conda env (Pangeo base + extras). Decision tree for a new dep: manylinux wheel → pyproject; conda-only AND only for local-dev/CI → `dev-conda-deps.txt`; conda-only AND needed in the hub image → `image/environment.yml`. Full reference: `docs/AUTOMATION.md`. Pre-consolidation there was a fourth file `hub-conda-deps.txt` that auto-synced to a separate image repo — gone after the consolidation.

    **Dev-tool gotcha (regression seen 2026-05-28):** when a *dev tool* (e.g. `tomlkit` for `tools/new_sensor.py`) ALSO runs on the hub (e.g. operators invoke the scaffolder from inside a notebook pod), it must be in **BOTH** `dev-conda-deps.txt` AND `image/environment.yml`. The first scaffolder rollout missed this — the conda dep was in `dev-conda-deps.txt` (CI happy) but not in `image/environment.yml` (hub pod failed with `ModuleNotFoundError: No module named 'tomlkit'`). If you add a runtime dep for anything under `tools/` that's documented as runnable on the hub, double-check both files.

13. **Embed COG metadata at creation, not as a post-step. GDAL 3.10+ rejects in-place update on a COG.** Validated 2026-05-29 against `det_hconf_filtered_h05v05_20180830.tif`: `gdal.Open(path, GA_Update); ds.SetMetadata(...)` raises `RuntimeError: ... has C(loud) O(ptimized) G(eoTIFF) layout. Updating it will generally result in losing part of the optimizations`. With the `IGNORE_COG_LAYOUT_BREAK=YES` open-option override the SetMetadata succeeds and tags roundtrip via GetMetadata — but `rio_cogeo.cogeo.cog_validate` then returns `valid=False` with 3 IFD-offset errors (main IFD shifts from <300 to 2394 bytes, overview IFD ordering is inverted). **The post-step pattern is dead.** This is why `shared_utils.cog_utils.convert_to_cog` switches from subprocess `rio cogeo create` to in-process `rio_cogeo.cog_translate(additional_cog_metadata=...)` whenever its `metadata=` kwarg is provided — embedding has to happen during creation. Do not reintroduce post-step `gdal.SetMetadata` for COG outputs. The `tests/unit/test_cog_metadata.py::TestConvertToCogMetadata` suite pins this contract.

14. **All sensor CLIs expose `--metadata-json <path>` and use the same parser helper.** Pattern: `metadata = shared_utils.cog_metadata.load_metadata_json(args.metadata_json)` immediately after `args = parser.parse_args()`, then thread `metadata=metadata` into every `convert_to_cog(...)` call site. The Landsat CLI has 13 call sites; Sentinel-2 has 12; the others have 1. The scaffolder template ([tools/_templates/sensor/process_name.py.tmpl](tools/_templates/sensor/process_name.py.tmpl)) is wired to inherit this on `python tools/new_sensor.py <name>`. Don't write a per-CLI parser; reuse `load_metadata_json`. Don't accept inline JSON strings on the CLI either — the helper takes a file path because shell-quoting nested JSON is a footgun, and the notebooks write to a tempfile anyway.

15. **Two-cell ACTIVATION_METADATA convention in every operator notebook.** Cell A (operator-edited, mixed into the existing CONFIG cell): `EVENT_NAME = 'YYYYMM_Hazard_Location'` + `SOURCE = "<sensor default>"`. Cell B (auto-populated, immediately below, **don't edit**): imports `PROCESSOR_STRING`, builds `ACTIVATION_METADATA`, then (subprocess-style notebooks only) dumps it to a temp JSON file as `ACTIVATION_METADATA_PATH`. The subprocess `process_cmd` then `.extend(["--metadata-json", ACTIVATION_METADATA_PATH])` right before `subprocess.run/Popen` or `sys.argv` + `main()`. The split exists to make "what an operator changes per activation" cleanly distinct from the dict-construction + JSON-write plumbing. The scaffolder ([tools/_templates/notebooks/workflow.py.tmpl](tools/_templates/notebooks/workflow.py.tmpl)) generates both cells for new sensors. Don't merge them back together; don't drop the JSON file (or `--metadata-json` becomes useless); don't hardcode `"PROCESSOR": "NASA Disasters COG Processor v1.0"` (use `PROCESSOR_STRING` from `shared_utils.version` so the value tracks the git tag automatically).

16. **Batch loops use `shared_utils.parallel.map_threaded`, not raw `for`-loops or `ProcessPoolExecutor`.** The one helper is `map_threaded(func, items, max_workers, desc) -> list` — preserves input order, captures per-item exceptions in-place (no batch crash on one bad item), optional tqdm progress bar. Threads-not-processes is intentional and pinned by rule #8: S3 I/O (boto3) and GDAL native calls both release the GIL, AND a ProcessPool would oversubscribe cores because each worker's `convert_to_cog` already spawns `NUM_THREADS=ALL_CPUS` internally. Worker counts pinned: **`max_workers=2`** when the worker is a full GDAL subprocess (`process_capella`/`process_umbra`/etc. — each subprocess saturates all cores; >2 thrashes), **`max_workers=4`** for in-process loops calling `convert_to_cog` / S3 upload directly. Pre-baked wrappers: `shared_utils.cog_processing.process_batch_s3(s3, bucket, [(src,dst),...], max_workers=4, **kwargs)` for the convert+upload pattern; `SimpleProcessor._process_category` parallelizes per category via `config['max_workers']`. Don't reintroduce ProcessPoolExecutor without a benchmark proving you've capped per-worker GDAL threads to avoid the oversubscription regression. Pinned by `tests/unit/test_parallel.py` and `tests/unit/test_cog_processing_batch.py`.

17. **All Python packages live under `src/` (src layout, since 2026-06-16).** `landsat`, `sentinel2`, `satellogic`, `umbra`, `capella`, `shared_utils`, `raster_tools` are at `src/<pkg>/`. `src/` is only a discovery root (`pyproject.toml [tool.setuptools.packages.find] where = ["src"]`), **not** part of the import path — so import names are UNCHANGED (`import shared_utils`, `from sentinel2.sentinel2_functions import *`) and `[project.scripts]` targets stay `<pkg>.cli:<verb>_cli`. Consequence: you must `pip install -e .` (or install the wheel) to import — you can't `import shared_utils` from the bare repo root anymore. Discovery tooling scans `src/`: `tools/check_sensor_consistency.py` (`SRC_DIR`), `tools/new_sensor.py` (scaffolds into `src/<name>/`), and the `.github/workflows/lint.yml` import-test. When adding a sensor manually, the dir goes in `src/`.

18. **Landsat merge path (`-merge`) — four pinned invariants (fixed 2026-06-29, commit `bef7b8e`).** The mosaic/merge code in `src/landsat/landsat89_functions.py` + the merge post-step in `process_landsat89.py` had six bugs around saving + filenames; the fixes are now load-bearing:
    - **`gen_merge` must NEVER reopen a source scene in `'w'` mode.** The old code reprojected mismatched-CRS inputs by `rio.open(tif, 'w', ...)` on the *source path* — silently overwriting (destroying) the operator's native-CRS input file, reachable on any cross-UTM-zone path/row span (and via `gen_water_extent`'s B5 merge). Mismatched scenes now reproject into a `tempfile.mkdtemp()` dir, get swapped into a local `merge_inputs` list, and the temp dir is removed in a `finally`. **Do not reintroduce in-place reprojection.** Pinned by `tests/integration/test_landsat_merge_pipeline.py::test_multicrs_merge_does_not_mutate_inputs`.
    - **`ls_merge` derives the merge date from `shared_utils.file_naming.extract_datetime_from_filename`, not positional `parts[2]`.** `parts[2]` is the *time* (HHMMSS) on already-renamed files (event prefixes were dropped 2026-06-16), so a re-merge produced names like `LC08_trueColor_190001_merged.tif`. It also **excludes any prior `*merged*.tif`** from its input glob (a `-force` re-merge folded the previous mosaic back in) and raises `FileNotFoundError` (not `IndexError`) on an empty dir.
    - **`rename_with_event` and `get_final_filename` (in `shared_utils/cog_utils.py`) are a lockstep predictor/actual pair** — the skip check (`get_final_filename` + `os.path.exists`) MUST predict exactly what the rename produces. For merged files the product token is `'_'.join(parts[1:date_index])` so multi-token sensor ids (Sentinel-2 `S2B_MSIL2A_<product>`) keep the real product. Any new "already exists?" skip check must glob the **post-rename** name via `get_final_filename`, never the raw pre-rename name (the waterExtent check did the latter → re-ran + re-uploaded every time when `--event` was set).
    - **The merge post-step's "rename the leftover individual scenes" logic is one helper, `rename_individual_scene_files(directory, event)`** (in `landsat89_functions.py`), called by both the cloud-mask loop and the product loop. It was copy-pasted inline and the cloud-mask copy referenced a stale `prod_dir` loop variable, renaming the wrong directory. Don't re-inline it.

19. **JupyterLab UI is customized via [`image/overrides.json`](image/overrides.json)**, baked into the hub image (COPYed to `/srv/conda/envs/notebook/share/jupyter/lab/settings/overrides.json`, the sys-prefix settings-override path). No extension, no node build — uses the built-in `help:open` command. Currently a `Help → Disasters Resources` submenu (added 2026-07-01, commit `c6a4a97`). Three gotchas when editing: (a) `@jupyterlab/mainmenu-extension` **MERGES** menu customizations with the defaults instead of *replacing* them (unlike every other plugin's `overrides.json`) — appending to `jp-mainmenu-help` preserves the built-in Help items, so don't re-declare them. (b) External links **must** set `"newBrowserTab": true`, else the URL opens in an in-lab iframe and GitHub / most SaaS render "refused to connect" (`X-Frame-Options: DENY`). (c) `label` is valid ONLY on the `submenu`/menu *object*, never on a menu *item* — a stray `label` (or any other unknown key) on an item fails schema validation (`additionalProperties` is false) and kills the WHOLE `mainmenu-extension` plugin (cascading into `help-extension:resources` + `mainmenu-extension:recents`), so nothing renders (fixed 2026-07-01, commit `06bd552`). Iterate without a rebuild by `-v`-mounting the file over the baked-in path; validate with `python -m json.tool image/overrides.json`. Editing it **does** trigger a hub rebuild (`image/**` is in the build workflows' `paths` allowlist). Full detail: `docs/HUB_DEPLOYMENT.md`.

20. **`.tif` matching is case-insensitive; local files normalize to lowercase `.tif` (added 2026-07-01).** CSDA vendor data ships **uppercase `.TIF`**, and Python `str.endswith(".tif")` is case-sensitive — so the old filters silently dropped every CSDA file. Two-part rule now:
    - **Detect** with `name.lower().endswith("<lowercase-literal>")` at every listing/selection predicate. The central one is `shared_utils.s3_operations.list_s3_files` (feeds the notebook file-listing cells, `batch_analyzer`, `notebook_helpers`). The SAR modules have their own inline predicates too: `capella_v2.py` (`.tif` + `_preview.tif`), `umbra_v2.py` (`.tif` + all four `_gec.tif` selectors), `satellogic_v2.py` (`.tif` + `_toa_0.tif` / `_cloud_0.tif`). If you add a `.tif` filter, lowercase both sides.
    - **Never lowercase the remote S3 key** returned by a listing/selector — the object really is `.TIF` on the bucket, so a lowercased key 404s on fetch. "Convert to `.tif`" happens on the **local working copy only**, via the single helper `shared_utils.s3utils.local_tif_basename(s3path)` (lowercases a `.tif`-family extension, leaves everything else — including tokens like `_GEC` — untouched). It's used by `download_s3_file` (names the /tmp file) and by the capella/umbra download-cache `glob` predicates (so the cache-hit check matches the normalized on-disk name). satellogic uses `download_s3_file`'s return value directly, so it inherits the fix.
    - **No output-side work needed** — all COG output names are already lowercase `.tif` by construction (`file_naming.create_output_filename` does `os.path.splitext()[0]` + a hardcoded `.tif`; every sensor `outfile` f-string ends in `.tif`). SAR basename-*parsing* (`base.replace(".tif","")`, `split("_")[n]`) reads early positional tokens, so an uppercase extension on the last token doesn't corrupt it — left as-is. Non-tif metadata selectors (`_angles.geojson`, `.json`) left case-sensitive (no evidence CSDA ships those uppercase). Pinned by `tests/unit/test_s3utils.py` (`TestLocalTifBasename`, `TestListS3FilesCaseInsensitive`, `TestDownloadS3FileNormalizesExtension`).

21. **The sensor dispatch scripts have no importable `main()` — cover the processing path with targeted tests, not `--help`.** `src/landsat/process_landsat89.py` runs its whole pipeline under `if __name__ == "__main__":`; `src/sentinel2/process_sentinel2.py` runs it at **bare module level** (so a plain `import sentinel2.process_sentinel2` would fire argparse). Neither exposes `main()`. Consequence: `cli-smoke` in `lint.yml` only runs `<cli> --help`, which argparse short-circuits **before** the dispatch loop — so a runtime `NameError` in the dispatch (classic case: a name like `cloudMask` still referenced by the index-product calls after its assignment is removed) is invisible to CI, and the dispatch can't be import-tested either. Two ways to cover it without a `main()` refactor or a full scene fixture: (a) **product code** — import + exercise `src/<sensor>/<sensor>_functions.py` directly (these `*_functions` modules import cleanly under the `tests/conftest.py` osgeo stub; e.g. call `apply_cloud_mask` on tiny rasterio-synthesized rasters — the 3-band path is pure rasterio, the 1-band path routes through gdal `dump_geotiff` so guard it with a real-GDAL skip); (b) **dispatch itself** — a `symtable` static check that flags any name *referenced-but-never-bound* at module scope in `process_*.py`, resolving `from X import *` by importing X (catches the undefined-name class statically). Don't treat `--help` as processing-path coverage. Both guards live in `tests/integration/`: `test_sensor_mask_smoke.py` (runtime) and `test_dispatch_undefined_names.py` (the symtable check).

22. **`-mask` masks *index products and water extent only*, never color composites (changed in #28, 2026-07-06).** `process_landsat89.py` / `process_sentinel2.py` pass the cloud mask to the index gen-functions (`genNdvi/genNdwi/genmNdwi/genEvi/genNbr` on Landsat; `gen_ndwi/gen_mndwi/gen_ndvi/gen_nbr` on S2) and to `gen_water_extent`, but pass `None` to the color composites (`genTrueColor/genNaturalColor/genColorInfrared/genPanchromatic`, plus S2 `gen_swir`). The gen-functions gate on `if mask is not None:` (not truthy `if mask:` — a mask can be an array). On the merge path, masking is gated by `is_index = os.path.basename(os.path.normpath(prod_dir)).lower() in {<index names>}` — an **exact product-folder basename** match (dirs are `NDVI/NDWI/MNDWI/EVI/NBR` vs `trueColor/naturalColor/...`), NOT a substring search (the old `any(x in prod_dir.lower() ...)` wrongly flagged paths containing `evi`/`nbr`, e.g. `.../preview/...`). Net: `-mask` no longer emits masked true-color/SWIR output — that's intended.

23. **`notebooks/sentinel2_workflow.ipynb`: `TILE_ID` is a *list*, and the CONFIG cell owns the credentials + `OUTPUT_DIR` setup (multi-tile support, dev 2026-07-06).** Three coupled invariants a config-cell edit MUST preserve — **none are caught by CI** (`.ipynb` files are neither linted nor smoke-tested by `lint.yml`; the only guard is reading the notebook end-to-end after editing the config cell):
    - **`TILE_ID` must be a Python list** — `["T17RLN", "T17RLM"]`, and a list even for one tile (`["T17RLN"]`). The download + process cells pass it as `"-tile", *TILE_ID` — a **wildcard-unpack** into the CLI's `-tile nargs='*'` arg (`download_sentinel2.py:41`, `process_sentinel2.py:59`). A scalar string would unpack into individual characters (`T`,`1`,`7`,...). `TILE_ID` (list) and `*TILE_ID` (unpack) are a **lockstep pair** — change one, change both; the doc-cell caution text (`#"-tile", *TILE_ID`) must match too.
    - **The config cell must call `load_env_local(...)` and set `COP_USER` / `COP_PASS`** (from a git-ignored `.env.local`, never hardcoded). The download cell references bare `COP_USER` / `COP_PASS`.
    - **The config cell must define `OUTPUT_DIR` + `os.makedirs(OUTPUT_DIR, exist_ok=True)`.** The download / process / upload cells all reference `OUTPUT_DIR`.
    A refactor that drops any of these `NameError`s at first run. Seen for real when an older *pre-multi-tile* config cell (scalar `TILE_ID`, no `OUTPUT_DIR`) got merged over the newer one — the notebook imported fine but died the moment the download cell ran. When resolving a merge conflict in this cell, prefer the side that keeps all three, then graft the list-`TILE_ID` on top.

24. **Satellogic vendor S3 layout + output naming (`src/satellogic/`, PR #33).** The `csda-data-vendor-satellogic/disasters/` bucket ships **two coexisting raster layouts** — code must handle both (confirmed from a live `aws s3 ls`):
    - **Vendor scenes** (dominant): `<folder>/rasters/<stem>_{TOA,CLOUD,VISUAL}_0.tif` — UPPERCASE, one tile per scene, band suffix `_0`. Folder = `<YYYYMMDD>_<HHMMSS>_[<captureid>_]<SAT>_<LEVEL>[_SR]_MS[_<order>]`; **L1D keeps the 3-digit capture-id** (`..._857_SN28_L1D_SR_MS`), **L1B omits it** (`..._SN41_L1B_MS_341273`).
    - **Analytic-tiled**: `<folder>/<stem>_<zone>_<col>_<row>_{analytic,cloud,visual}.tif` — lowercase, **many tiles per scene**, no `rasters/` subdir, UTM grid `<zone>_<col>_<row>` (e.g. `19N_724_1158`) in the name.
    Invariants pinned in `satellogic_v2.py` / `process_satellogic.py`:
    - `retrieve_satellogic_resources` selects tifs by **file extension**, not by a `rasters/` subdir (works for both layouts, but also picks up any stray `.tif` sidecar in the folder). The level filter is a substring `f"_{level}_"` on the **folder** name; datetime comes from the folder's `parts[0:2]`.
    - `group_satellogic_tifs` matches each image's `cloud`/`visual` companion by **lowercased suffix** and returns the **real-case S3 key** (rule 20 — CSDA ships uppercase `.TIF`; an exact-case-mismatched or lowercased key 404s). Only `_analytic.tif` / `_toa_0.tif` files count as images.
    - **Masking is hardcoded per product family (PR #45, 2026-07-21) — no `--use_mask` flag anymore.** The five product fns dropped the `use_mask` param and pass it explicitly at the call site: color composites (`genTrueColor`/`gencolorIR`) call `prepare_scene(..., use_mask=False)` (never mask clouds); indices (`genNDVI`/`genNDWI`/`genEVI`) pass `use_mask=True` and gate on `if cloud is not None:` (a cloud-less scene warns + proceeds — never `gdal.Open(None)`). `prepare_scene` still fetches/opens the cloud band only when `use_mask=True`.

27. **Product filename convention — one shared transform; `_day` ⟺ merged/time-less, ISO-Zulu `Z` ⟺ individual-with-time (2026-07-16, `fix/pr27-review-followups`).** `shared_utils.cog_utils._relocate_datetime(base_name, ext)` is the single source of the rename rule, called by **both** `rename_with_event` (the actual rename) and `get_final_filename` (the skip-check predictor) so they can't drift — pinned by `tests/unit/test_landsat_merge_naming.py::test_predictor_and_rename_stay_in_lockstep`. **The rule (Landsat AND Sentinel-2):** a **merged** mosaic → `..._merged_YYYY-MM-DD_day.tif` (date only — a mosaic spans multiple acquisition times); an **individual scene WITH a time** → `..._YYYY-MM-DDTHH:MM:SSZ.tif` (full ISO-Zulu; the trailing `Z` is the completion marker, no `_day`); an **individual with NO time** (e.g. `waterExtent`) → `..._YYYY-MM-DD_day.tif`. That restored the "one filename module" rule #31 broke **and** fixed a real `ValueError` crash: #31's inline regex could not parse an already-renamed `_day` scene, so a `-force` re-merge over renamed scenes raised `ValueError: Could not extract date/time`. `s2_merge` already emits a date-only merged name, so it needed no change. Walks every `.tif`/`.TIF` under it (via `s3_operations.list_s3_files`, the only case-insensitive `.tif` filter) and classifies each in this order: (1) **already-baked** — object already has a valid `ACTIVATION_EVENT` tag → **skip** (idempotent); (2) **matched** — basename matches `cog_metadata.DEFAULT_ACTIVATION_PATTERN` (`^(\d{6})_([A-Za-z0-9]+)_([A-Za-z0-9]+)_(.*)\.tif$`, compiled `IGNORECASE`) → new key = same folder + **group(4) + `.tif`** (the `YYYYMM_Hazard_Location_` prefix is stripped OUT of the filename; the event goes into the tags, not the name); (3) **unmatched** — no valid prefix, or a `name_collision` (two sources → same new key, or new key already exists as a different object) → written to a **local** `needs_event.csv` (`bucket,key,filename,reason,cog,ACTIVATION_EVENT`). `bake_s3()`: `get_object` bytes → re-encode via in-memory `create_cog_with_metadata(src_bytes, meta, output_path=None, preserve_compression=True, target_crs=None, web_optimized=False, blockxsize/blockysize/overview_level read from source)` → `bytes(out)` (defensive; `cog_metadata._read_vsimem` was fixed 2026-07-28 to return `bytes`, but older installs returned a `bytearray` that `MemoryFile`/`put_object` reject — see CLAUDE.md Critical Constraints) → structural `_verify_bytes` (valid COG + CRS/dims/count/dtype/nodata/transform match source + event tag present) → `put_object(new_key)` → `head_object` confirm → `delete_object(old_key)` **only if `new_key != key`**. The idempotency skip is enforced **authoritatively inside `bake_s3`** from the just-downloaded bytes (the scan's `/vsis3` tag pre-read is only for the dry-run report and degrades gracefully). **Input-COG flag + auto-convert (2026-07-29):** the scan probes each object once (`probe_s3` → existing tag + `cog_validate`) and reports whether each input is already a COG (report lines + a `cog` column in the CSV); `bake_s3` preserves a COG input's structure/compression but **converts a non-COG** to a COG with default settings (512² tiles, 5 overviews, ZSTD via `preserve_compression=False`) — pixels/CRS/nodata stay identical (`_verify_bytes` gates it), and the result dict carries `converted`. **Parallel scan (2026-07-29):** probing 30k+ object headers serially is slow, so the scan fans `probe_s3` across a THREAD pool (`SCAN_WORKERS`, default 16; execute/bulk-fix use `PROCESS_WORKERS`, default 8) — threads, NOT multiprocessing (the work is GIL-releasing network/GDAL I/O, one boto3 client is thread-safe and shared, sized via `botocore Config(max_pool_connections=max(SCAN,PROCESS,10))`; processes would pickle/recreate the client per worker). **Report cell MERGES** any `ACTIVATION_EVENT` already filled in a prior `needs_event.csv` so re-scanning / "Run All" never wipes operator edits. **Bulk-fix** section: reads the (operator-filled) CSV and bakes those in place (`new_key == key`; no prefix to strip, so filename unchanged). `DRY_RUN=True` is the default — top cells only report (nothing uploaded/deleted). **Credentials:** ambient `boto3.client('s3', region_name='us-west-2')` is correct for `nasa-disasters` (same-account `disasters-prod` on the hub) — **NO assume-role** (vendor/CSDA reads on DPS also use the worker's ambient creds — the old `READ_ROLE_ARN` assume was removed 2026-07-31); `s3_operations.setup_vsi_credentials(s3)` exports the client's creds to GDAL env for `/vsis3`. **Design decisions (locked by the user):** S3-only (not dual local+S3); in-place rename + delete old key (not a separate dest prefix); structural (fast) verify (not sampled pixels). **Testing:** pinned by `tests/unit/test_bake_metadata_s3.py`, which **execs the notebook's real code cells** (not a reimplementation) against a `moto` (`mock_aws`) bucket, forcing `/vsis3` to fail fast (`AWS_S3_ENDPOINT=localhost:1`) so `read_event_s3` exercises its `get_object` fallback. 5 tests: classification + dry-run-is-readonly (+ COG flag); execute rename+delete + bit-identical pixels (`np.array_equal`) + tags + valid COG; idempotent re-run; CSV bulk-fix in place; non-COG input flagged + converted to a valid COG. Runs in CI's `pytest tests/` job (module-guarded by `importorskip` for moto/osgeo/`shared_utils.cog_metadata`/nbformat). **VEDA note:** the notebook validates COGs with `rio_cogeo.cog_validate` locally because `dev.disasters.openveda.cloud/api/raster` is a titiler-pgstac *mosaic* API (`/searches/...` only, no `/cog/validate`).

34. **Sentinel-2 Copernicus download runs one UNAUTHENTICATED catalog search per tile, and the search loop is now never-silent (`src/sentinel2/download_sentinel2.py`, hardened 2026-07-29 on `fix/bake-cog-flag-convert`).** Operator symptom that triggered this: "9 tiles searched, only 5 products downloaded." **There is NO per-file cap** — `-limit` is the OData `$top` page size (default **50**, DPS config default 50, notebook passes none → 50), and the loop does **NOT** follow `@odata.nextLink`, so it reads exactly one page per query. "9 → 5" meant **4 tile queries returned an empty `value` list (or errored) and were silently dropped** by the old `json = requests.get(url).json(); if json.get('value'):` pattern (no `status_code` check, no `error`-key check). **The fix:** a `search_catalogue(url) -> (products, error)` helper (mirrors the existing `get_keycloak` error-wrap style — `raise_for_status()`, JSON-parse guard, OData `error`-key check; **never raises**), and all three search branches (tile/polygon/point) now **log one line per query** — `tile T17RLN → N product(s)` / `tile T17RLN → 0 products ⚠` / `tile T17RLN → search FAILED (<reason>) ⚠` — with an end-of-run summary listing every missing/failed tile plus the likely causes (Sentinel-2 revisit ≈ 5 days ⇒ a single `-date` only catches tiles under that day's orbit swath, widen `-date` to a start/end range; wrong `-level` 1=L1C vs 2=L2A; a `search FAILED` line = transient API error, re-run). `prods_to_download.extend(prods)` is unconditional (empty/error → `[]`, so safe). Warn-and-continue (a partial result is still useful), mirroring the download loop's own per-file `try/except`. **Non-obvious testing lever:** the catalog search (`catalogue.dataspace.copernicus.eu/odata/v1/Products`, public) runs **before** `get_keycloak` (the bearer token is only needed for the `zipper.dataspace.copernicus.eu/.../$value` download), so the per-tile logging can be **smoke-tested creds-free** — `download_sentinel2 /tmp/x -tile T17RLN T99ZZZ -date 20230116 -level 2 -u fake -p fake -y` prints the real per-tile lines against live CDSE, then 401s at keycloak (expected, past the code under test). **No test in `tests/` imports/execs/mocks this script's search**, so the output change broke nothing — but that also means this path is unpinned; verify by running the CLI. Scope was strictly the logging/error hardening — **no** `-limit` bump and **no** `nextLink` pagination were added (if a single tile/date legitimately exceeds `limit` results, extras are still dropped — revisit only if that case appears).

35. **`cog_metadata` in-memory (`/vsimem`) COG paths MUST be unique per call — they are thread-shared and race (fixed 2026-07-30 on `fix/bake-cog-flag-convert`).** `/vsimem/` is a **process-global** in-memory filesystem. `create_cog_with_metadata`'s bytes path (`_create_cog_in_memory`) and `validate_cog_in_memory` used **hardcoded constant** vsimem paths (`/vsimem/cog_meta_input.tif`, `/vsimem/cog_meta_output.tif`, and `/vsimem/validate_out.tif` — the latter because `bake_s3._verify_bytes` always passes the constant `"out.tif"`). `notebooks/bake_event_metadata.ipynb` fans `bake_s3` out over `map_threaded(max_workers=PROCESS_WORKERS=8)`, so 8 threads read/wrote the **same three files** → torn reads. **Operator symptom:** the same activation, run on the hub, reported a scatter of per-file failures — `IndexError('list index out of range')`, `RuntimeError('unknown error occurred')`, `Could not read /vsimem/cog_meta_output.tif`, `RasterioIOError('No such file or directory')`, a `_verify_bytes` `['geotransform changed']` (compared against a *different* file's bytes), and `cog_validate` spam `The offset of the main IFD should be < 300. It is 1132 instead` + `TIFFReadDirectory:Invalid data type for tag TileOffsets/TileByteCounts` — **all torn-read artifacts of the same race, not a data/GDAL-version problem** (the IFD/TileOffsets lines are just `cog_validate`'s non-quiet stdout). **The fix:** `import uuid`; every vsimem path is now `f'/vsimem/..._{uuid.uuid4().hex}...'` (input+output share one `_uid`). **Proof it was concurrency:** identical files bake perfectly **sequentially** (`max_workers=1` → 0/16 fail) and fail **concurrently** on the *old* constant paths (`max_workers=8` → 15/16 fail with those exact errors); unique paths → 0/16. **Why every prior test missed it:** `test_bake_metadata_s3.py` only ever bakes **one** matched file per run (the other seeded objects are collisions/unmatched), so it never exercised ≥2 concurrent bakes. New pin: `tests/unit/test_cog_metadata.py::TestInMemoryThreadSafety` (32 tasks × 8 workers through `create_cog_with_metadata`+`validate_cog_in_memory`) — **fails on constant paths, passes on the uuid fix**. **General rule:** any new `gdal.FileFromMemBuffer` / `/vsimem/<literal>` in a function that could be called under `map_threaded` (or any thread pool) MUST use a per-call-unique suffix; rasterio's own `MemoryFile` already auto-generates unique vsimem names, so prefer it where possible.

## Patterns to follow

- **One filename module**: `shared_utils/file_naming.py` is the single source of truth for `extract_datetime_from_filename`, `categorize_file`, `create_output_filename`, `no_change`, `DATETIME_PATTERNS`. Notebooks should `from shared_utils.file_naming import ...`, not redefine. The earlier legacy helpers (`extract_date_from_filename`, `convert_date`, `parse_filename_components`, `create_cog_filename`, `create_output_path`) were deleted — their behavior is covered by the new API plus plain `os.path.join`. If you find them referenced in old code, replace with the new helpers. **The rename side** (relocating date/time to the canonical output convention — rule 27) lives in `cog_utils`: `_relocate_datetime` is the one transform behind both `rename_with_event` and `get_final_filename`, and `ls_merge`/`s2_merge` take their merge date from `file_naming.extract_datetime_from_filename` — don't re-inline datetime parsing in a sensor module.
- **One Web-Mercator-clip detector**: `shared_utils/reprojection.needs_webmerc_clip(src_or_path, dst_crs)` returns True iff the source's geographic lat bounds exceed ±85.05° AND `dst_crs` ≈ EPSG:3857. Returns False for the 99% regional-raster case (no behavior change for sensor pipelines). Used by `cog_utils.convert_to_cog` and the CLI notebook.
- **Notebook tiers stay paired**: `notebooks/<x>.ipynb` (Hub/CLI subprocess style, has Quarto YAML) and `notebooks/testing-notebooks/<x>.ipynb` (import-based, for local dev). They should differ only in *style*, not behavior — both pull from the same `shared_utils` helpers.
  - **A CLI-side policy change reaches the top tier for free and SILENTLY MISSES the testing tier.** The top notebook shells out to `process_<sensor>`, so anything hardcoded in the CLI is inherited. The testing notebook calls the library directly and therefore **re-implements policy inline** — e.g. `notebooks/testing-notebooks/satellogic_workflow.ipynb` carried its own `nodata = -9999 if <index> else 0` and its own `COMPRESSION_LEVEL`, which would have re-broken every composite the alpha-band fix repaired (rule 45). **When you change a hardcoded CLI constant, grep the testing tier for a duplicate of it.** Neither tier is linted or smoke-tested in CI.
- **`.ipynb` `source` must stay a LINE-ARRAY, never a single string.** Both forms are valid nbformat and both render fine, but a tool that writes `"source": "line1\nline2"` turns a 5-line edit into a ~130-line diff (the whole cell reads as deleted + re-added), which makes notebook review useless. After any programmatic edit, normalize: `c['source'] = c['source'].splitlines(keepends=True)` for every cell, then `json.dump(nb, f, indent=1, ensure_ascii=False)` + a trailing newline — that matches what `nbformat` writes, so the diff stays minimal. Check with `git diff --stat` before committing: a config-value edit should be single-digit lines. Validate afterwards by `json.load`-ing and `ast.parse`-ing each code cell (skip cells with `!`/`%` magics).
- **`simple_disaster_template.ipynb` ships an identical pre-wired 15-category config block in both tiers** — nisar, trueColor, colorInfrared, naturalColor, shortwaveIR, ndvi, mndwi, ndwi, waterExtent, blackmarble, cloudMask, nbr, dnbr, ssrun, psh, each with a `CATEGORIZATION_PATTERNS` regex + `FILENAME_CREATORS` builder + `OUTPUT_DIRS` subdir + `NODATA_VALUES` entry (added 2026-07-01, commit `d869555`; `nisar` added 2026-08-25, rule 48). Keep the block byte-identical across the two notebooks. **This is easy to half-do and the test suite will not shout:** `test_simple_disaster_naming.py` parametrizes over both notebooks but *skips* the category-specific checks on a tier that lacks the category, so adding one to a single tier goes green — PR #127 shipped `nisar` to the top tier only and the drift showed up as 10 silent skips, not a failure. After adding a category, confirm the run reports **0 skipped**. **`CATEGORIZATION_PATTERNS` is first-match-wins** — order overlapping tokens: `nisar` first (`NISAR|GUNW` must win before any loose optical substring), `dnbr` before `nbr` (`'dNBR'` contains `'NBR'`), `mndwi` before `ndwi`, and keep `trueColor`'s `tc` bounded as `(?:^|[_-])tc(?=[_.-]|$)` so it doesn't match inside words ("catchment"). `OUTPUT_DIRS` are RELATIVE subdirs (the S3 dest-key builder / `SimpleProcessor` prepends the base) — never leave one empty (→ `//` key). Validate edits by exec'ing the config cell over one filename per category.
- New CLI scripts: add entry point under `[project.scripts]` in `pyproject.toml`, add the package to `[tool.setuptools.packages.find].include`. Sensor pipelines and standalone utilities both use the thin `cli.py` exec-wrapper pattern (see `src/landsat/cli.py` or `src/raster_tools/cli.py`). Full walkthrough in `docs/ADDING_FUNCTIONS_TUTORIAL.md`.
- **Test fixtures with real data go in `tests/fixtures/`**, kept small (<500KB) and DEFLATE-compressed with `predictor=3` for float32. Crop from production rasters with `rasterio.windows.Window` + `window_transform` to preserve georeferencing. Hard-code the expected min/max/mean in the test so re-cropping forces an explicit update (see `tests/unit/test_summarize_raster.py::test_summarize_raster_on_real_gaia_atlanta`).
- **Tests must import from the submodule, not the package root** — `from shared_utils.cog_utils import X`, not `from shared_utils import X`. The package `__init__.py` chains optional imports including `cog_metadata`, which calls `gdal.UseExceptions()` at module load. On environments with a GDAL python-binding / dylib mismatch (common on dev laptops, see hard rule #6) this raises `AttributeError`, which the `try/except ImportError` in `__init__.py` does not catch — every test that touches the package root then fails at collection. Submodule imports skip the broken chain.
- COG defaults: ZSTD level 22, 512x512 tiles, 5 overview levels. Nodata auto: uint8=0, int16=-9999, float=-9999.0.

## Patterns to avoid

- Don't introduce new `convert_to_cog` symbols in `shared_utils/` — there are already two (`cog_utils.convert_to_cog` and `main_processor.convert_to_cog` aliased as `convert_to_cog_s3`); a third risks star-import shadowing. They have different roles: the former is the local-file warp+COG primitive; the latter is the S3 download → engine → upload orchestrator that delegates to the former. **Don't re-implement warp+COG logic in main_processor — it's a thin wrapper.**
- Don't reintroduce the chunk_config / size-based branching that used to live in `main_processor.convert_to_cog`. It was deleted in the unification refactor because `gdalwarp` + `rio cogeo create` handle their own chunking via `BLOCKSIZE` and `NUM_THREADS=ALL_CPUS`.
- Don't commit `.ipynb_checkpoints/*` or `__pycache__/*` — both are in `.gitignore` but tend to leak in during merges.

## Architecture quick map

- `shared_utils/cog_utils.convert_to_cog(input_tif, output_cog=None, dst_crs='EPSG:3857', resampling_method=None, clip_to_webmerc=None, ...)` — **the engine**. Takes a local path (or `/vsi*` URI), runs `gdalwarp` (with auto-clip when needed) + `rio cogeo create`, writes a local COG.
- `shared_utils/main_processor.convert_to_cog(name, bucket, ..., target_crs='EPSG:3857', stream_from_s3=True, ...)` — **the S3 orchestrator** (~216 lines, was ~520). Probes `/vsis3/...` streaming first, falls back to `/tmp` download, calls `cog_utils.convert_to_cog`, validates, uploads to S3.
- `shared_utils/notebook_helpers.SimpleProcessor` — config-driven class wrapper used by GAIA / simple_disaster templates. Delegates filename/categorization to `shared_utils.file_naming`, delegates conversion to `main_processor.convert_to_cog`. Accepts `target_crs`, `resampling`, `clip_to_webmerc`, `stream_from_s3`, `compression`, `compression_level` config keys. **Compression forwarding was added 2026-07-01** — `_process_category` previously dropped compression settings, so every SimpleProcessor output silently used the library default 22; it now passes `config.get('compression'/'compression_level', 'ZSTD'/22)`. The `simple_disaster_template` notebooks expose `COMPRESSION_LEVEL` (default `9`); library-wide default stays 22.
- `shared_utils/reprojection.py` — pure-rasterio warp helpers + `needs_webmerc_clip()` + `WEBMERC_EXTENT_M` / `WEBMERC_EPSGS` constants.
- `tools/check_sensor_consistency.py` — pyproject ↔ sensor-dir consistency lint. Runs locally in <1s; runs in CI via `.github/workflows/lint.yml` `sensor-consistency` job. Catches the bug class that broke the capella rollout (script registered, package not installable).
- `dev-conda-deps.txt` — single source of truth for local-dev / CI conda deps. Distinct from `hub-conda-deps.txt` (which is what gets synced into the hub image's `environment.yml`). Most things in `dev-conda-deps.txt` are already in Pangeo base, so they don't appear in `hub-conda-deps.txt` — that file is for hub-image-specific overrides only.
- `.github/workflows/lint.yml` — two jobs (`sensor-consistency`, `cli-smoke`). The `cli-smoke` job installs from `dev-conda-deps.txt` + `pip install .` and runs `--help` on every console script in `pyproject.toml [project.scripts]`, catching the "shim without package" failure mode.

## Downstream dependency

Output COGs are read by `veda-data-airflow` DAGs (separate repo). The `build_stac` task is the strictest consumer — fix CRS issues here, not there. Two production failure modes to be aware of:
- **WGS 84 ensemble + lat-first axis** — kills `rio_stac.get_dataset_geom`. Mitigated by defaulting to EPSG:3857.
- **Source extent outside target CRS domain** — global Mollweide / polar stereographic warped to EPSG:3857 without a ±85° clip produces 50+ GB nonsense or fails. Mitigated by `needs_webmerc_clip()` auto-detect.

## MAAP DPS

DPS algorithm definitions live in `dps/` (full guide: `docs/DPS.md`). When editing them:
- `algorithm_name` must be `^[a-z0-9_-]+$` (lowercase, no spaces/slashes). Use `base_container_url`, not `docker_container_url`. Prefix `build_command`/`run_command` with the repo dir name (`disasters-product-algorithms/dps/...`). `inputs` is a flat list; types limited to string/int/File/Directory/long/float/boolean/double (no enum/array) — optional = `string` + `default: ""`, toggles = `boolean`.
- run.sh receives `--name value` flags (CWL), not positionals. Keep the shared output flow in `dps/_finalize.sh`; don't inline it per sensor.
- **Each run.sh boolean default MUST mirror its `algorithm_config.yaml` default** (not a blanket `false`). If MAAP omits a default-valued boolean at submit, a `false` run.sh default silently inverts the toggle — e.g. landsat `merge`/`mask` (yaml `true`) would run OFF while the form shows ON. Fixed 2026-07-16: landsat `merge`+`mask`→`true`, s2 `merge`→`true`; s2 `mask`, capella/umbra `apply_filter`, satellogic `visualize` stay `false` (yaml `false`). (Satellogic's `use_mask` boolean was removed in PR #45 — masking is now hardcoded, not an input. The `enable_s3_upload`/`delete_cog`/`save_png` booleans were later removed as job inputs for **all** sensors — publishing to `nasa-disasters-staging` + the scratch-COG delete are now locked always-on constants, and DPS produces no PNGs; see `docs/DPS.md` "All sensors → nasa-disasters-staging".)
- **Fail-fast input validation lives in the shared `dps/_validate.sh`** (sourced by every run.sh, called right after flag parsing, *before* conda/staging/S3; added 2026-07-17 on `fix/pr27-review-followups`). WHY it must exist: the OGC/CWL schema is `{name,label,doc,type,default}` only — **no enum/pattern/min-max** — so run.sh is the ONLY place a bad arg can be caught; otherwise it fails late inside gdalwarp or, worse, "succeeds" with zero output. A second test asserts the reverse for `algorithm_config.yaml`: a declared input with no `run.sh` parse case is a dead form field. 38. **Deleting (undeploying) a DPS algorithm is API-only, keyed by `processID`, and a rename does NOT move a process (2026-08-11, PR #92).** The MAAP **Register Algorithm GUI registers but cannot delete** — undeploying is a `DELETE` against the OGC processes API, and the ready-made tool is **`dps/delete_algorithm.ipynb`** (kernel **`disasters_dps`**, the env `build-env.sh` builds, which pins `maap-py`; the hub's default kernel also has `maap-py` from the MAAP base image). Flow: `MAAP()._get_api_header()` → `GET`/`DELETE` on **`https://api.maap-project.org/api/ogc/processes[/<processID>]`**. **The non-obvious parts:** (a) **you delete by the numeric `processID`** MAAP assigns at registration, **never by `algorithm_name`** — a name in the URL just `404`s, so the notebook always lists first and refuses any ID absent from the current listing; (b) codes are **`200`** undeployed / **`403`** you are not the deployer / **`404`** no such ID, and **only the deployer can delete their own process** — a `403` on something that looks like yours usually means the token belongs to a different MAAP account than the one that registered it (registered from the ADE, deleting from the Disasters hub, or vice versa: check `deployedBy`); (c) **this base URL carries an `/api` suffix**, the exact opposite of the JupyterLab extensions' `maapApiUrl` setting, which must have **none** (the extensions append it) — getting it backwards returns HTML → `Unexpected token '<'`; (d) `processID` is per **name+version**, so deleting `foo:dev` leaves `foo:v1.2.0` registered; (e) **delete removes the registration only** — running jobs are not cancelled, job history stays, outputs already in `nasa-disasters-staging/dps_output/<event>/` stay, the built container stays, and re-registering the same name afterwards gets a **new** `processID`. `_get_api_header()` is a **private** maap-py helper (returns `{Accept, Content-Type, token}` + a `proxy-ticket` when `MAAP_PGT` is set) — it survived the 4.2.0 → 5.1.0 OGC migration, but it's the thing to check first if the notebook stops authenticating. Still on the old split: `capella`, `landsat` (`landsat-8-9`), `satellogic`, `list_dates`.** Each migration leaves **up to two stale processes** (the bare GUI name + the `-ogc-test` name) that only this notebook can remove — the old `sentinel-2` was deleted this way on 2026-08-11. 39. **The "chevron icons everywhere" Lab UI bug (2i2c-org/infrastructure#8770) is the MAAP DPS/Algorithms extensions' `overflow: scroll !important` — NOT `jupyterlab-bxplorer` (corrected 2026-08-11; the first version of this rule blamed bxplorer and was wrong).** **Symptom:** small chevron/arrow pairs scattered over the *entire* Lab UI — menu bar, every file-browser toolbar button (each button gets its own pair), the breadcrumb, the `Name | Modified` header, the tab bar — plus a vertically clipped menu bar, while Launcher tiles below render at normal size. 41. **MAAP Settings (API URL / PGT) reset on every login because `maap-jupyter-server-extension` clobbers the user-settings file with `""` on every page load — an upstream bug, not a persistence problem (2026-08-12, issue #88).** **Symptom:** an operator pastes a MAAP API URL + PGT into Settings → MAAP Settings, runs an algorithm, logs back in, and both fields are blank. **The misleading part:** the values DO land in `~/.jupyter/lab/user-settings/maap-jupyter-server-extension/plugin.jupyterlab-settings` on the persistent home volume, and they persist perfectly on an image *without* the MAAP extensions — which reads as "the hub config overrides user settings" but is the opposite: something in the MAAP image actively **overwrites** them. **Root cause, `src/index.ts` @ v3.0.0** (the version `maap-workspaces/base_images/2i2c/pangeo` pins): on **every JupyterLab page load** the plugin `GET`s `{baseUrl}maap-jupyter-server-extension/get-maap-params` and pushes all five settings back with `serverExtSettings.set(...)` — **unconditionally, with no guard for empty values**. `ISettings.set()` PATCHes `/lab/api/settings/<plugin-id>`, which is precisely what writes that file. The server half (`handlers.py::GetMaapParamsHandler`) reads `MAAP_PGT` / `MAAP_API_HOST` / `DOCKERIMAGE_PATH_DEFAULT` / `DOCKERIMAGE_PATH_BASE_IMAGE` / `WORKSPACE_BUCKET` from the environment and returns `""` for each unset one. MAAP injects those per-pod from its ADE devfile (`maap-workspaces/devfiles/pangeo/devfile/devfile.yaml`: `MAAP_API_HOST: api.dit.maap-project.org`); **the Disasters hub is not a MAAP-managed hub**, so nothing sets them → `""` → clobber. **Repro loop is a browser hard-refresh, NOT a pod restart** — set the fields, hard-refresh, re-`cat` the file: already wiped, with `Successfully updated MAAP extension settings.` in the DevTools console. Anyone debugging this by rebuilding + promoting `dev`→`main` + restarting the pod is using a loop hours longer than necessary (and see rule 40 for the trap waiting at the end of it). **The shipped fix is two halves, because the two fields differ in kind.** (a) **`ENV MAAP_API_HOST=api.maap-project.org` in `image/Dockerfile`** — identical for every operator, so setting it makes the clobber write the *correct* URL instead of `""`; it also gives a new user a working default (**the PGT prompt only appears once a URL exists** — that is why step 3 in the issue was flaky), and `maap-py` reads the same var so bare `MAAP()` stops depending on ambient config. The value is a **bare hostname — no scheme, no `/api` suffix**: `format_api_url()` prepends `https://` and appends a trailing slash, the consuming extensions' `joinUrl()` strips that slash again, and maap-py's scheme is `MAAP_API_HOST_SCHEME` (default `https`). (b) **`image/scripts/fix_maap_settings_clobber.py`** rewrites each `R.set("<key>", V)` in the installed bundle to `(V?R.set(/*disasters-settings-guard*/"<key>",V):Promise.resolve())` — write only a non-empty value, leave a saved one alone, keep auto-population wherever the env var IS set. The token is per-user and secret so it **cannot** be baked into an image; it has to survive in the settings file, which is what this buys. **Design points that are load-bearing:** the value pattern excludes parens/commas because both receiver and value are emitted twice (so it matches property reads and bare identifiers — what the minifier emits — and refuses anything that could be a call with side effects); the marker between `set(` and the quote makes a guarded call unmatchable, giving idempotency for free; and the script is **scoped to files containing `get-maap-params`** so it never touches the *user-initiated* `settings.set('maapApiUrl', ...)` in `dps-jupyter-extension`/`algorithms-jupyter-extension` (guarding that one would stop an operator deliberately clearing a field). **It is STRICT BY DEFAULT, deliberately unlike `fix_lm_widget_overflow.py` (rule 39):** missing bundle, zero matches, or any unguarded write surviving the pass each fail the image build (`--lenient` downgrades the first two; a surviving unguarded write fails regardless). A silent miss here is invisible in the UI and puts operators straight back on the re-paste-every-login treadmill. **Verified against the REAL bundle, not just a reconstruction:** `pip download maap-jupyter-server-extension==3.0.1` → unzip → run the script over the wheel's `*.data/data/share/jupyter/labextensions` tree; all five writes guarded, idempotent on re-run, output parses clean. The bundle ships **unminified** (readable `serverExtSettings.set('maapApiUrl', maapParams.maapApiUrl),`), so the pattern has far more slack than a mangled build would give it. ⚠ **Use the 3.0.1 wheel, never 3.0.0** — the published **3.0.0 wheel is a stale build** carrying the untouched cookiecutter placeholder (`jupyter-server-extension:plugin`, a lone `requestAPI('get_example')`, zero settings code), while *both* wheels' internal `package.json` reports `3.0.0`. It does not reflect git tag `v3.0.0`, whose `src/index.ts` does carry the writes; harmless for the hub, which installs `git+...@v3.0.0` and builds from source, but it will send anyone verifying via PyPI to the wrong conclusion ("there is no clobber"). **The leftover check must use a LOOSER pattern than the rewrite** — the first version reused the strict one, so a call the rewrite was too strict to match (e.g. a value wrapped in `String(...)`) was skipped *and* reported as a clean run; caught by a synthetic-bundle battery before shipping. **The real fix is upstream** in `MAAP-Project/jupyter-server-extension` (~3 lines guarding the `set()` calls). 45. **`convert_to_cog(nodata=...)` is a THREE-way contract resolved by TYPE, and a scalar nodata SHADOWS an alpha band (2026-08-13, supersedes the "composites → 0" row of disasters-portal #320).** **Symptom:** Satellogic true-color/color-IR COGs rendered their legitimately-black imagery as nodata. `process_satellogic.py` declared `nodata=0` on a uint8 composite where **0 is a perfectly ordinary sample** — dark water, shadow, burn scar — so every such pixel read as "no data". **Fix:** `genTrueColor`/`gencolorIR` now write a **4th `GCI_AlphaBand`** via `geotools.dump_geotiff_rgb(..., alpha=<uint8>)` and pass **`nodata=False`**. **The contract, and why each branch exists:**
    - `None` (default) → inherit the source's tag, else auto-detect from dtype.
    - `<number>` → declare verbatim, after `validate_nodata_for_dtype`.
    - `False` → declare NO nodata; for inputs carrying their own alpha/mask band.
    - `True` → **ValueError**, deliberately.
    **Resolution is by TYPE (`isinstance(nodata, (bool, np.bool_))`), never `is False` and never truthiness.** Three separate traps forced that: (a) `bool` subclasses `int`, so an unguarded `True` sails through `validate_nodata_for_dtype` as the numeric `1` and gets declared; (b) `0 == False` is True in Python, so any `==`/truthiness test collapses the two branches that must stay distinct; (c) **`np.False_ is False` is `False`** — a numpy-derived flag (very easy to produce from a numpy expression) would miss an identity check and fall through to numeric validation as 0. The bool branch is placed **before** the `is None` branch.
    **`nodata=False` must also STRIP a tag the source already carries — passing `None` downstream is NOT sufficient.** Both `rio cogeo create` and `rio_cogeo.cog_translate` do `nodata = nodata if nodata is not None else src_dst.nodata`, so an opt-out on a producer that writes a nodata tag is **silently ignored**. `convert_to_cog` therefore runs a `gdal_translate -of VRT -a_nodata none` step first (a VRT is a lazy XML header — no pixel copy) and points the warp + COG steps at it. **Only the PIXEL SOURCE is redirected: `input_tif` keeps pointing at the real file**, because its basename is load-bearing — `resolve_metadata()` parses the activation event out of it and `determine_resampling_method()` reads it; redirecting it makes HAZARD/LOCATION derive from `...nonodata.tmp.vrt`. The VRT is removed at all three cleanup sites (success + both except paths). This is invisible for Satellogic today (`dump_geotiff_rgb` writes no nodata tag) and matters the moment another sensor adopts `False`.
    **Why alpha rather than Capella's border-fill (rule 37):** Capella's float32 dB has an unambiguous out-of-range sentinel (`-9999.0`), so writing it INTO the border makes the declared nodata and the actual fill agree. A uint8 composite has **no** spare value — every one of 0–255 is legitimate — so the validity has to live outside the pixel values. **Do not "simplify" this back to a scalar.**
    **The two are not composable — a scalar nodata declared alongside an alpha band WINS.** rasterio says so outright (`NodataShadowWarning: the dataset's nodata attribute is shadowing the alpha band. All masks will be determined by the nodata attribute`) and rio-cogeo warns `"Input dataset has both a nodata value and internal alpha/mask band. Nodata value will be prioritized."` Measured on a 4-band RGBA fixture: `read_masks([1,2,3])` (what titiler does for an RGB render) returns **0 over black-but-valid imagery** with `nodata=0`, and **255** with `nodata=False`. Note `dataset_mask()` alone is a misleading check here — it's the union across all 4 bands, so the alpha band's own 255s can make a shadowed file look fine.
    **The trap this shipped with:** `notebooks/testing-notebooks/satellogic_workflow.ipynb` is the **direct-library** path (calls `genTrueColor`/`gencolorIR` then `convert_to_cog` itself) and carried its own inline `nodata = -9999 if <index> else 0`, which would have re-broken every composite the alpha band was added to fix — while the top-level `notebooks/satellogic_workflow.ipynb`, which shells out to the CLI, inherited the fix for free. **Both Satellogic notebooks must be updated together**; the CLI is not the only caller. Both previews now stack band 4 as a matplotlib alpha channel so the border renders transparent instead of black.
    **Still outstanding:** `sentinel2_functions.py` calls `dump_geotiff_rgb` at 4 sites and `landsat89_functions.genTrueColor` builds composites the same way — both still declare `nodata=0` and have the identical latent bug. `dump_geotiff_rgb`'s `alpha=None` default keeps them byte-identical for now. **Pinned by** `tests/unit/test_cog_utils.py` (`TestNodataSentinelResolution`, `TestNodataFalseStripsSourceTag`, `TestNodataBoolGuard`, `TestNodataVersusAlphaBand`), `tests/unit/test_geotools.py`, `tests/unit/test_satellogic_composites.py` (the last monkeypatches `prepare_scene` so the real band-math → mask → writer path runs without S3). **Also in this change:** Satellogic's `compression_level` became the module constant `COMPRESSION_LEVEL = 9` (PR #106 as submitted had `1`, a test leftover; the library-wide default stays 22).

46. **Black Marble products were misregistered by ~3.6 km to the NORTH-WEST for their entire history — an UPSTREAM window-arithmetic bug, and the most invisible class of defect we have shipped (2026-08-13, disasters-portal#365).** **Symptom as reported:** "the COG viewer images don't look right." Nothing else. **Every conventional check passes**, which is why this survived: the COG's transform is *exactly* `blackmarble.crs.create_processing_grid(bbox, 30)`, its WGS84 bounds match the requested bbox to 5 dp, `rio cogeo validate` passes, `gdalinfo` looks perfect, and in a viewer the layer lands over the correct city. Only the **pixel content** is displaced. **Measured**, by phase-correlating the delivered COG against the OSM road network rasterized onto the same grid: Suomi-NPP `dy=-117 px (-3.51 km), dx=-93 px (-2.79 km)`; NOAA-20 `dy=-116, dx=-91`. Both platforms, so it is the shared pipeline, not the NOAA-20 retarget. **Root cause — `blackmarble/prepare/landsat.py` (~line 509, in `process_landsat_date`):** the band mosaic path allocates `tile_data_reprojected = np.zeros((dst_height, dst_width))` sized to `dst_window_int`, then calls `reproject(..., dst_transform=band_profile["transform"])` — the **full-mosaic** transform — and finally pastes the result into the mosaic at `dst_window_int`'s offsets via `calculate_window_offsets`. `dst_transform` declares where destination pixel (0,0) *is*, so handing it the mosaic's transform renders tile content at mosaic coordinates into an array whose (0,0) is really the window's corner; the paste then applies the window origin a **second** time. `MARGIN_PIXELS = 120` ("~3.6km at 30m resolution", expanding the read window to avoid gaps at UTM zone boundaries) is what makes that origin large and negative — for the SF bbox `dst_window_int` is `row_off=-124, col_off=-120`. **That is the 3.6 km, exactly.** The QA/cloud-mask path 250 lines *above in the same file* does it correctly (`dst_transform=rasterio.windows.transform(dst_window, qa_profile["transform"])`), so the cloud mask and the bands it masks were on different grids. **Predicted-vs-measured is the proof**: replaying upstream's own window arithmetic for the SF bbox against a UTM-10N source predicts `(-124, -120)` px and the delivered COG measures `(-117, -93)` — the E–W component reads smaller than predicted because the composite blends shifted Landsat with unshifted VIIRS, pulling the centroid toward zero. **The fix is `dps/blackmarble/bm_georef.py`**, a monkeypatch (never a fork — CLAUDE.md forbids re-vendoring blackmarble, and the SHA pin in `dps/environment.yml` stays intact) that swaps in `rasterio.windows.transform(dst_window_int, transform)`. **Use the ROUNDED window, not the float `dst_window` upstream's QA path uses** — the rounded one is what sizes the destination array *and* what the paste offsets use, so deriving the transform from the float window leaves a residual sub-pixel shear between the three. **Patch mechanics:** two cooperating wrappers, because `reproject` alone cannot know which window it is filling — `round_window_offsets_correctly` stashes `(window, transform)` on its way out and `reproject` consumes it, firing **only** when `dst_transform is` the stashed transform object (identity, not equality — the correct QA call builds a *new* `Affine` from the same mosaic transform and an equality test would match it) **and** the destination's shape is exactly the window's. The stash is **consumed on first use** so it can never leak into upstream's single-file branches, which legitimately pass the mosaic transform with a mosaic-sized destination. **`MARGIN_PIXELS = 0` is the documented emergency fallback** — it also removes the error (a zero-width margin makes the double-application free, measured ≤80 m) but works by disabling the UTM-boundary gap protection, trading a georeferencing bug for a seam bug on wide AOIs. **THE FAILURE MODE IS A SILENT NO-OP**, same as rule 44: a stale patch simply would not fire and the job would publish a misregistered COG and exit 0, with a patch file next to it claiming otherwise. So `apply_georef_patch()` validates upstream's shape first and raises, and **`bm_georef.py --self-check` is wired into `dps/Dockerfile`'s smoke gate** — it re-runs that validation *and* pushes markers at known coordinates through the patched path offline (no token, no network, no AWS), asserting they land within 200 m; unpatched they land ~3600 m out or off the grid entirely. **Both platforms now enter through a shim**: `run.sh`'s snpp branch calls `bm_georef.py` instead of the bare `blackmarble` console script, and `bm_noaa.py` applies the georef patch too (idempotent, disjoint symbols, order-independent). **Diagnostic technique worth reusing:** binary overlap between a lit-pixel mask and rasterized roads constrains E–W well but **cannot see a N–S shift at all** when the coastline runs north–south — it reported `dy≈0` against a true `dy=-117`. FFT **phase correlation** on the smoothed luminance vs a smoothed road-density raster recovers both axes. Two earlier attempts also failed and are worth not repeating: a landmark bright/dark test (Golden Gate Park and Twin Peaks are *not* dark in the contrast-enhanced product) and an IoU sweep against `osmnx.geocode_to_gdf("San Francisco")` (that returns the **county**, which covers open water — 82.8% of the frame). **Reference evidence** is committed at `tests/fixtures/blackmarble_sf_misregistered_crop.tif` (65 KB crop of a real published product, carrying the defect). **This belongs upstream** at `NASA-IMPACT/veda-black-marble` — file it, and delete `bm_georef.py` the moment a fixed release is pinned; `test_upstream_still_has_the_defect` fails loudly when that happens. **Also in this change (separate concern, same file):** `bake_event.py` now passes **`target_crs='EPSG:3857'`** instead of `None`, because upstream writes a **per-bbox ad-hoc Albers with no EPSG authority code** (`crs.to_epsg()` is `None`; the WKT literally reads `PROJCS["unknown", GEOGCS["unknown", ...]]`) built by `blackmarble.crs.make_local_albers()`, with no CLI flag / config field / env var to change it — and an authority-less CRS is what breaks `veda-data-airflow`'s `build_stac` (`rio_stac.get_dataset_geom`). **Setting `target_crs` silently DESTROYS every upstream tag**, which is a trap worth its own sentence: `create_cog_with_metadata` wraps the source in a `WarpedVRT` when reprojecting, a WarpedVRT carries **no** dataset tags, so `cog_translate` has nothing to copy and `data_sources` (the full granule list — the one tag that cannot be reconstructed afterwards), `bbox`, `producer`, `processing_steps`, `indices` and `creation_date` all vanish. `bake_event._carry_forward_tags()` re-supplies them explicitly, rewriting the two the warp invalidates: `crs` (upstream's proj4 string, now `EPSG:3857`) and `resolution` (upstream's `30.0` Albers metres — Web Mercator metres are not ground metres, and at this latitude the `1/cos(lat)` scale factor makes the output pixel **37.94 m**, computed via `calculate_default_transform` and pinned by a test against the actual raster). The pre-warp projection is preserved as **`SOURCE_CRS`** (WKT) + `SOURCE_CRS_PROJ4` — it has no EPSG code, so it is genuinely unique to that product and bounding box and is unrecoverable once the raster is Mercator; keeping it makes the resampling auditable and the native grid reconstructible. **The `wgs84` job input is NOT the fix for any of this** and was a red herring in the original report: upstream treats `--wgs84` as a *secondary export* (`pipeline.py:577-601`) that writes an extra `<stem>_wgs84.tif` of the **colored** raster only, leaves the primary product in the local Albers, emits the EPSG:4326 that breaks `build_stac`, and produces a name with a token after the date (violating rule 43's convention, since `run.sh` renames only the `-colored` companion).

50. **Satellogic ships the OPPOSITE RGB band order at its two processing levels — resolve it PER SCENE, never positionally (2026-08-25, issue #118).** `satellogic_v2` hardcoded `red=band3, green=band2, blue=band1` and applied it to every scene. That is the **L1D** layout; **L1B is reversed** (`band1=red, band2=green, band3=blue`). `level` was already threaded from `prepare_scene` into all five product functions but was consumed **only** by `maybe_correct` for the solar-zenith correction — there was zero level-conditional band logic. **Affected:** `genTrueColor` (red/blue transposed), `gencolorIR` (reads blue where it means red), `genNDVI` (computed from blue, which TOA Rayleigh scattering inflates → systematically depressed), `genEVI` (blue and red transposed). **`genNDWI` was NEVER affected** — it uses bands 2 and 4, which are identical under both layouts; it is the control that shows a fix moves only what the transposition touched. **The fix is `resolve_band_indices(ds, level)`**, called in all five (ndwi included, so no positional index can creep back in): it prefers the file's own `ColorInterp` and falls back to `BAND_ORDER[level]`. **Three traps in the ColorInterp read, all load-bearing:** (a) GDAL defaults band 1 of a plain multi-band TIFF to **`Gray`** and the rest to `Undefined`, so a partial declaration is a DRIVER DEFAULT, not a vendor statement — `band_order_from_colorinterp` returns `None` unless red+green+blue are each declared **exactly once**; (b) the vendor declares **no ColorInterp for band 4 (nir)** even on files where 1-3 are set, so NIR is inferred as the single leftover band and the whole read is rejected if there is not exactly one; (c) a 3-band uint8 file auto-reports R/G/B from photometric RGB — that is why the *committed* `VISUAL_0` crop looks declared while the 4-band `TOA_0` crop reports `Gray/Undefined`. **The fallback path is the common one, not an edge case:** `create_segment_file` in `tests/vendor-test-data/test-data-downloader.ipynb` rebuilds crops from rasterio's `src.meta`, which carries **no** colorinterp, so every committed Satellogic fixture has it stripped. **`resolve_band_indices` always PRINTS which source decided the mapping** — a wrong band order is invisible in the output because `normalize_band` stretches each band independently, so the composite still reads as a plausible photograph. That is exactly why this shipped unnoticed. **Evidence (L1D, both vendor-declared and functionally measured):** the STAC `eo:bands` on the `analytic` asset (band1 blue 480nm / band2 green 545 / band3 red 640 / band4 nir 825) and the sibling `_TOA.vrt`'s `<ColorInterp>` elements agree; scoring generated truecolor against the vendor's own `VISUAL_0` gives a correlation diagonal of **+0.9883** with the L1D mapping vs **+0.9538** swapped — and the fix leaves that number **bit-identical**, which is the regression that matters since L1D is the default level. **The L1B ColorInterp claim itself is NOT independently verified in-repo** — the CSDA vendor bucket is readable only from the MAAP DPS worker role / hub, not from laptop SSO (all six SSO account+role combinations return `AccessDenied`), and no L1B scene is committed. It rests on issue #118's measurement; the ColorInterp-first design is deliberately robust to it, since a file that declares its own order overrides `BAND_ORDER` either way. **Also added: a `PROCESSING_LEVEL` GeoTIFF tag** (`process_satellogic.py`, `setdefault` on the metadata dict, guarded on `is not None` so it does NOT flip the no-metadata path from the gdalwarp/rio-cogeo subprocess backend to in-process `cog_translate`). Without it the level is unrecoverable from a published product — the vendor capture id (present on L1D, absent on L1B) is the only other tell and the event rename strips it — which is why the blast radius of this bug could not be bounded from S3. Every published Satellogic product that still carries a capture id is L1D and therefore correct. Pinned by `tests/unit/test_satellogic_band_order.py`. **Footgun for any test that predicts an 8-bit output value** (not just Satellogic): the writer casts with `.astype(np.uint8)`, which **TRUNCATES**, and the float32 scale lands just UNDER the exact value, so truncation drops a whole count — `2000 * 1e-4 * 255` is `51` in exact arithmetic but `50.999996` in float32. Worse, the multiply must be **in-place** to reproduce it: under numpy 1.x value-based casting `np.float32(2000) * 1e-4` promotes to **float64** and yields exactly `0.2` (→ 51), while `load_reflectance_band`'s `arr *= scale_factor` stays float32 (→ 50). **Replay the real arithmetic in the test rather than hand-computing the expected DN** — hand-computing produced two rounds of false failures that looked like band-routing bugs and were not.
